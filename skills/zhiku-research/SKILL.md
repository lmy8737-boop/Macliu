# 知库深研（zhiku-research）

把研究变成可长期更新的 Markdown 资产。本 skill 用于 Obsidian（或同类双向链接笔记工具）里的原文、双链、底表和跟踪体系；如果你还需要生成对外分享的 PDF/正式报告，那是另一件事，本包不含这层。

知识库根：`<你自己的知识库根目录>/`——按你实际使用的 Obsidian vault 或笔记目录调整，本 skill 不假设固定路径。

写库硬门禁以本包 `../../references/知识库写入规范.md` 为准（若你的工作区另有自己的 `AGENTS.md`/任务路由/投研总规则文件，以你自己工作区的版本优先）。先定位旧文，能原位更新就不新建。

## 两种模式

| 模式 | 触发 | 读取与产出 |
|---|---|---|
| `PATCH_NOTE` | 用户指向既有原文/问题，或明确要求对既有节点做有边界的财报、事件、数据、打分、评级、估值、双链或格式更新 | 只读目标段、必要上下文、母专题目录和受影响底表；回答受影响问题，并按因果影响联动结论、评级、估值和跟踪项，不强跑全文框架 |
| `FULL_NOTE` | 新公司/新行业正式深研、全文重构、用户明确要求完整报告 | 执行完整关键问题、章节框架和 playbook；建立或重构长期节点 |

先按用户问题的实际范围选模式，不能只因“已有目标文件”就判为 PATCH。仅当改动能被既有节点和明确章节容纳、且不需要重建完整投资论点时使用 `PATCH_NOTE`；用户要求正式深研、全景重构或问题跨越多数核心章节时使用 `FULL_NOTE`。只有原文无法容纳独立主题，或目标确实是新的长期研究节点，才新建文件。

## 输出位置

| 产出 | 目录 | 命名 |
|---|---|---|
| 个股深度 | `03_公司研究/<赛道>/` | `<中文公司名>.md`；已有同名页原位更新 |
| 稳定横向对比 | 对应公司/行业目录 | `<主题>对比专栏.md` |
| 阶段性对比复盘 | 对应公司/行业目录 | `<YYYY-MM-DD> <主题>对比复盘.md` |
| 行业/产业链 | `04_行业研究/<板块>/` | 稳定节点不改名；阶段性事件才带日期 |

先搜母专题、公司页和索引，再动笔。稳定节点更新 `updated`，不因每次更新改文件名。

## 硬规则

1. **工具按数据所有权调用，不机械跑三件套**：`stock-data` 负责 T0/T1 与结构化金融数据；`brm-mcp` 在需要研报、纪要、专家和订单线索时调用；联网检索与官网原文统一交给 `web-harvest`。正式深研应覆盖足够来源，但不要求每次把三者全部调用。失败时记录真实失败层和替代路径。
2. **时效**：T0 只用当日实时源，禁用 BRM；PE = 实时价 ÷ 对应预测 EPS，自行复算。T1 核到最新季度和时间戳；本次会引用、复算或据以修改结论的旧 T0/T1 必须先刷新。纯机械双链、锚点、标题或格式修复若不触及金融数据和判断，不强制刷新无关 T0/T1。
3. **问题范围**：`FULL_NOTE` 回答相关的 12 个关键问题；`PATCH_NOTE` 只回答用户追问和被新信息影响的问题，不为凑格式写无关“不适用”。
4. **口径红线**：份额、市场规模、财年、算力、出货量、收入/利润和 CFO/FCF 必须标口径，禁止混用。
5. **证据字段各管一件事，不可互相替代、不可混用**：统一引用 `research-data-verify/SKILL.md` 的「Canonical Evidence Semantics」。

   | 字段 | 管什么 | 规范取值 | 常见错误 |
   |---|---|---|---|
   | `source_level` | 来源权威性 | `P0/P1/P2/P3` | 把 P0 当“已验证”，或把工具名当等级 |
   | `claim_type` | 主张类型 | `fact/third_party_view/guidance/model/scenario` | 把卖方预测、指引或场景写成事实 |
   | `verification_status` | 验证状态 | `original_checked/independent_cross_checked/single_source_unverified/conflicted/unverified` | 单份 P0 自动升级为独立双源 |
   | `retrieval_status` | 获取状态 | `ok/partial/empty/stale/error` | 把“取到数据”当“已验证”，或不单列 `as_of` |
   | `K1/K2/K3` | 后续**跟踪频率** | K1 高频 / K2 季度·事件 / K3 慢变量 | 写成 P1/P2/P3，与证据级混淆 |

   两个独立信息链对同一口径数字差异≤2% 才是 `independent_cross_checked`（旧 `[V]`）；单份 P0 是 `original_checked`。旧 `[A]/[S]/[E]/[X]/[N/A]` 只按 canonical 兼容映射解释，不用于新表主字段。场景假设必须单列，不与事实混写。
6. **跟踪频率不用 P1/P2/P3**：统一写 `K1` 高频、`K2` 季度/事件、`K3` 慢变量，避免与证据等级混淆；每项附绿灯、红灯和下次更新触发。
7. **双链**：公司中文名用 `[[中文公司名]]`，英文名放 `aliases`；正文不用管道别名。`related` 按需填写真正相关节点，旧文补反向链接。
8. **结论不谄媚**：用户判断先验证；区分市场共识、本库差异化判断、催化剂和证伪条件。主题研究必须有最强反方。
9. **业务拆分**：FULL 公司深研遇到两条以上业务线，给分段收入、增速、毛利率和核心客户表。PATCH 只在新信息影响这些字段时更新对应行。
10. **订单与第二曲线**：分为公告/客户点名/推断/传闻；第二曲线分为已有收入、有客户但占比小、仅规划无订单。
11. **原位回写与底表优先**：新信息先改受影响底表和原文章节，再按因果影响联动打分、评级、估值、结论四格和跟踪项；新证据订正旧结论时保留删除线。同步分支索引、`知识库更新总索引.md` 和可复用结构化数据。
12. **配图**：仅用户明确要求图解时调用 你自己的配图工具（如果有）；工具失败要明说，不用 Mermaid 或文字冒充已生图。
13. **判断复盘（分析性 PATCH_NOTE 更新已有公司/主题页的前置动作）**：财报、事件、数据、打分、评级或估值更新前，先读原文最近一次的评级、结论四格、关键跟踪指标（K1/K2/K3）及其日期，用 1-3 句写清"上次判断 vs 现在实际发生了什么"（对/错/部分对，附证据），再写新内容；判断被推翻保留删除线原文，不静默替换。本条验证的是**分析师自己的结论**，不是打分体系本身（如果你维护了独立的打分校准回路，见《打分体系回测方法》），也不是管理层承诺兑现（如果你维护了独立的管理层承诺跟踪表）——三者互不替代。纯机械链接/格式 PATCH 和全新 `FULL_NOTE` 首次建页没有历史判断可复盘，跳过不算缺项。
14. **原文问答**：用户在笔记中以 `> [!question]` 提问时，在其下方写入 `> [!answer]`；回答范围仍按问题及其联动影响控制，不借问答扩成无关全文。

## frontmatter

公司 FULL_NOTE 示例：

```yaml
---
title: <中文公司名>
ticker: <代码>
exchange: <交易所>
aliases: [<英文名>, <代码>]
date: YYYY-MM-DD
updated: YYYY-MM-DD
rating: <立场和关键提醒>
tags: [公司研究, <市场>, <赛道>]
related:
  - "[[<行业母专题>]]"
status: tracking
---
```

行业、主题或 PATCH 不强制填写 `ticker`、`exchange`、`current_price` 等无关字段。来源应写在正文和数据核查表中，不为凑 frontmatter 罗列未调用工具。

## 三种内容形态

1. **个股深度**：商业模式、业务拆分、财务、竞争、估值、风险和跟踪。
2. **横向对比**：对比总表、本质分野、逐公司差异、估值与适用情景，不机械平铺。
3. **源头地基**：需求定义者、产品路线图、出货时间表、BOM 与价值量迁移，联动下游专题。

`FULL_NOTE` 或结构性重写才读取 `references/playbook.md` 的案例与句式库；普通 `PATCH_NOTE` 不加载。下面「首稿自检清单」由两种模式在内部执行，但只检查本轮实际触发的条目；不输出无关“不适用”，也不借自检扩大任务范围。

## 首稿自检清单（写完必过一遍，目标是一把成文不返工）

从 179 条历史追问归纳。先在内部判断触发项；命中的主动覆盖，不等用户追问，未命中的不写“不适用”。

**内容完整性**

| # | 触发场景 | 首稿必须做到 |
|---|---|---|
| 1 | 有 ≥2 条业务线 | 给分段收入 + 增速 + 毛利率 + 核心客户表，不能只给总数 |
| 2 | 出现专业名词/英文缩写 | 首次出现就用类比+例子解释（知识库是自用学习工具，不是对外报告） |
| 3 | 涉及受益标的 | 候选池默认全球，不要只给 A 股；只给 A 股必须说明理由 |
| 4 | 说某公司是"核心供应商" | 按四级分级：已披露订单 > 客户点名 > capex/招标推断 > 供应链传闻；拆到工序 |
| 5 | 任何核心论断 | 必须带数字；没有数字就明写"下一步补哪个数据" |
| 6 | BOM/架构/技术路线 | 类比+步骤讲清；用户点名要图才调 你自己的配图工具（如果有） |
| 7 | 提到第二曲线 | 三类分开：已有收入 / 有客户但占比小 / 仅规划无订单 |
| 8 | 出现传言或大额预测 | 自上而下 × 自下而上交叉反推，验数量级是否可能 |
| 9 | 列了 >8 家公司 | 另给 5-6 家精选短名单，不让用户自己筛 |
| 10 | 需要持续跟踪 | 做成 K1/K2/K3 框架 + 红绿灯触发条件，不写一次性结论 |

**判断质量**

| # | 触发场景 | 首稿必须做到 |
|---|---|---|
| 11 | 用户给了判断或倾向 | 先验证再展开，不顺着说；错了直接指出 |
| 12 | 财报季更新 | 上季预测 vs 实际预期差表 → 拆"涨跌是 price in 还是真新变量" → 电话会指引单独成节 → 原位更新打分卡，并按影响联动评级/估值；只有用户明确提出交易意图时才另答"能不能买"并升相应风险流程 |
| 13 | 用户引用第三方 App 数据（"富途显示XX倍"） | 先分辨口径差异 vs 数据错误：GAAP/非GAAP、TTM/forward、一次性项、前复权；给两口径对照表，结论常是"两边都对" |
| 14 | 用户给定参数要求照算 | 先确认单位口径（万/吨 vs 元/kg，不二次猜）；按给定参数照算不劝退；给敏感性表；偏离公开数据只一次性标注 |
| 15 | 数据似乎找不到 | 声称"无数据"前先自建：stock-data K线+EPS → BRM → web 一手源；标口径与误差 |
| 16 | 多标的比较/排名；或明确仓位请求 | 比较/排名只给横评维度表和排名理由；仅用户明确要求仓位或再平衡时输出权重%（不给绝对金额）和触发条件，并按 R 级标人工裁决 |
| 17 | 排版与链接 | `[[中文公司名]]` 双链、标题层级和锚点正确；纯机械修复不强制刷新未触及的 T0/T1 |
| 18 | FULL_NOTE 个股深研 | 必须带一张 3-5 家同业 PE/增速/毛利率横评小表（口径一致、标注报告期，对标候选不限于 A 股），单独的横向对比专栏才展开完整对比；快诊/追问场景不强制 |

## FULL_NOTE 章节参考

执行摘要 → 业务与产业位置 → 分段收入/毛利/客户 → 财务与现金流 → 竞争和技术壁垒 → 订单/capex/产能 → 三情景与估值 → 最强反方和风险 → 结论四格 → K1/K2/K3 跟踪 → 数据核查表。

可按主题裁剪，章节服务问题，不追求固定长度。「竞争和技术壁垒」或「核心逻辑」相关章节须显式拆**短期逻辑**（题材/催化剂，2-3点，说明具体事件与公司关联）与**长期逻辑**（壁垒/成长驱动，2-4点，需数据或竞争分析支撑），不得混写成一段笼统叙述——"值不值得现在追"和"值不值得长期拿"是两个问题，答案可能相反。

## 调研大纲（按需衍生，非默认产出）

**不是**独立报告章节，**不**默认生成。仅当用户明确说"准备去调研/参加交流会/联系IR"等场景才触发。做法：把当前报告里的未决 A 级变量（`verification_status` 为 `single_source_unverified/conflicted/unverified`）和 K1 级追踪指标，逐条转成问句格式（背景 1-2 句 + 具体问题），直接复用已有变量表和 K1/K2/K3 追踪表的内容，不重新分析、不产生新论断。跟踪表服务"不接触、持续盯数据"的日常场景（默认、高频使用）；调研大纲服务"要见人、需要提前想清楚问什么"的低频场景，互不替代、不强制同时产出。

## 工作流

1. 判断 `PATCH_NOTE` / `FULL_NOTE`，定位目标文件、母专题和底表。
2. 按 `investment-team` 确认 G/Y/R、关键变量、角色和证据要求。
3. 按数据所有权调用 stock-data / BRM / web-harvest；刷新本轮引用、复算或影响判断的 T0/T1，纯机械链接/格式修复除外。
4. PATCH：原段回答、受影响底表、打分/评级/估值/结论/跟踪项联动、双链与索引。FULL：完成框架、来源和结构化沉淀。
5. 写后检查目标存在、标题锚点、双链、索引、重复稿、结构化表唯一键和时间戳。
6. 交付只说明核心结论、实际修改文件、数据/工具缺口和验证结果，不复述整篇正文。

## 交付边界

- 未同步原文、底表和相关索引，不得称“已回写”。
- 未调用的工具不写成已调用；工具不可用不等于能力不存在。
- 永久正文默认不写流程回执；需要留痕时写任务日志或更新日志。
